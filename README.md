# LLM と RAG 勉強会まとめ

## 1. 勉強会の目的

- AI・機械学習・深層学習の違いを整理する
- LLM の基本的な仕組みを理解する
- RAG の考え方と構成を理解する
- 今後の実装に向けた前提をそろえる

## 2. AI・機械学習・深層学習

- AI
  - 知的な振る舞いを行うコンピュータ技術の総称
  - ルールベースの仕組みも含む
- 機械学習
  - データから規則やパターンを学習する手法
- 深層学習
  - 多層のニューラルネットワークを用いる手法
  - 計算資源の向上とデータ量の増加で実用化が進んだ

## 3. ニューラルネットワークと深層学習の補足

- ニューラルネットワーク
  - 人間の脳を参考にしたモデル
  - 入力から重要な特徴を抽出して出力する
- 深層学習
  - 層を深くすることで複雑な特徴を扱える
- RNN の例
  - 時系列や自然言語など、前の情報を踏まえた処理が可能
  - ただし長い文脈の保持や並列化は苦手

## 4. LLM とは何か

- LLM = 大規模言語モデル
- 大量データ・大量パラメータ・大量計算で学習した言語モデル
- 入力文脈に対して次に続く単語を予測して文章を生成する
- 現在は Transformer ベースが主流

### 主な特徴

- 要約
- 翻訳
- 情報整理
- 文書生成
- プログラミング支援
- 分析支援

### 注意点

- 正しい内容を保証するものではない
- もっとも続きそうな単語列を生成している
- 業務利用では人による確認が必要

## 5. 代表的な LLM

- GPT
- Claude
- Gemini
- LLaMA
- Qwen
- Gemma
- DeepSeek
- Swallow
- LLM-jp

### 公開形態

- クローズドモデル
  - API や GUI 経由で利用
- オープンモデル
  - モデルを取得してローカル利用可能

## 6. LLM を支えるアーキテクチャ

### Transformer

- 現在の LLM の中心となる構造
- Attention により単語同士の関係を扱う
- 長距離の依存関係を比較的保持しやすい
- 並列化しやすく大規模化に向いている

### モデルの種類

- エンコーダモデル
  - 入力の特徴抽出が得意
- デコーダモデル
  - 文章生成が得意
- エンコーダ・デコーダモデル
  - 変換タスクが得意

### 生成 AI で主流の系統

- デコーダ系モデルが中心

## 7. LLM の学習

- 事前学習
  - 大量テキストから一般的な知識や言語パターンを学ぶ
- 指示チューニング
  - 指示に従った応答ができるようにする
- アライメント
  - 安全性や望ましい振る舞いに近づける

### 勉強会で出た論点

- 後段の学習ほど出力傾向に影響しやすい
- 学習だけで安全性を 100% 担保するのは難しい
- 必要に応じてアプリ側の制御も必要

## 8. LLM の今後の方向性

- マルチモーダル化
  - 画像・音声も扱う方向
- LLM 生成文の検出
  - フェイクニュース対策など
- エージェント型 LLM
  - 計画、ツール利用、進捗分析
- 学習・推論の効率化
- 倫理性、信頼性、安全性の向上

## 9. ローカル LLM の補足

- 軽量化技術
  - 量子化
  - 枝刈り
- 目的
  - ローカル環境でも動かしやすくする
- 注意点
  - モデル形式によっては安全上の懸念がある
  - `safetensors` や `gguf` のような形式が比較的安全

## 10. RAG とは何か

- RAG = Retrieval-Augmented Generation
- 日本語では「検索拡張生成」
- 外部データベースや文書から情報を検索し、その結果をもとに LLM が回答する仕組み

### 基本フロー

1. ユーザーが質問する
2. 関連情報を外部データから検索する
3. 質問と検索結果を LLM に入力する
4. LLM が回答を生成する

## 11. RAG の効果

- LLM が学習していない情報にも対応しやすい
- 社内文書や部門固有情報を活用できる
- ドメイン知識に基づく回答をしやすい

### 注意点

- 間違った外部情報を入れると誤回答につながる
- データ品質が重要
- 検索性能が重要

## 12. RAG の検索方式

- キーワード検索
  - 単語一致を重視
- ベクトル検索
  - 文章の意味的な近さを重視
- ハイブリッド検索
  - 両方を組み合わせる

### ベクトル検索の要点

- 文を数値ベクトルに変換して比較する
- この変換を埋め込み（Embedding）という
- 類似度計算ではコサイン類似度がよく使われる
- 表現が違っても意味が近い文を探しやすい

## 13. RAG 設計で重要な点

- 文書をどの単位で分割するか
  - チャンク設計
- 何をインデックス化するか
- どの検索方式を使うか
- 上位何件を LLM に渡すか

### 精度に影響する要素

- データの持ち方
- チャンクの切り方
- 検索ロジック
- LLM に渡す文脈の作り方

## 14. 実装で使える主なツール

- LangChain
  - LLM アプリの機能拡張を効率化
- LlamaIndex
  - 外部データ連携を進めやすい
- Ollama
  - ローカルで LLM を動かしやすい

### 今回の方針

- まずは仕組み理解を優先
- フレームワークに頼りすぎず基本構成を押さえる

## 15. 今回想定している RAG 構成

- アプリケーションが質問を受け付ける
- Embedding model が質問をベクトル化する
- Knowledge Store から関連情報を検索する
- LLM が質問と検索結果をもとに回答する

### 環境

- 技統保有の Azure 環境を利用予定

## 16. 今後の改善ポイント

- インデックス設計の工夫
- クエリリライト
- ReRanking
- プロンプト設計
- モデルやパラメータの調整
- チャンク間の関係性の表現

## 17. まとめ

- LLM は Transformer を基盤とした大規模な言語モデル
- 幅広い用途に使えるが、出力の正しさは保証されない
- RAG は外部知識を使って回答品質を高める仕組み
- RAG の品質はデータ整備・検索設計・チャンク設計に強く依存する
- 今後は Azure 環境での実装と精度改善を通じて理解を深める
